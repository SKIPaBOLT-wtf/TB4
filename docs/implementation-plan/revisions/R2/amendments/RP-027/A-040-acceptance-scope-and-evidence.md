## Clarify the existing division of work

RP-027 delivers the staged, resumable reconfiguration transaction and its trusted
controller/admission interfaces. Its four original checks remain unchanged.
Actual first-run validation, preserved work/profile evidence, storage and
topology/launcher changes, fresh role/source/credential/physical checks,
conditional publication, pending recovery and no replay must be demonstrated
through the implemented composition. A controller declaration or a test count
alone does not satisfy these requirements.

A035's phrase "coherent runtime/GUI/controller composition" was ambiguous about
the later graphical feature. For RP-027, the required boundary is the actual
CandidateController with a fresh trusted checker factory, loss of stale UI
readiness on failure, and the native transaction/Main/admission composition.
The inspected implementation retains DenyActivation; it does not expose a
complete Qt reconfiguration screen. Canonical RP-053.C2 owns that screen and
correlated pending/success/conflict/unknown feedback, together with its required
UI tests. This clarification records that existing allocation explicitly; it
does not accept RP-053 or reduce any RP-027 transaction or negative predicate.

RP-030 retains the later expanded interruption matrix across commissioning,
reconfiguration and reset. RP-027 still needs its own current crash, fallback,
lost-access, exact pending-byte and preservation evidence before acceptance.
Later integration, packaged feature exposure and authorized field/pilot gates
remain separate. Existing package startup/installation checks establish their
declared scope, not an unimplemented graphical operation.
