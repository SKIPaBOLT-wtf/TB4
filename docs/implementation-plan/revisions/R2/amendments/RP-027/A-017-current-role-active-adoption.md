# A-017: Current-role adoption of an already ACTIVE native Docs configuration

Status: public implementation refinement under the owner-authorized RP-027
direction. It does not authorize an installed deployment, migration or effect
replay. Historical A-001 through A-016 contracts remain available.

An expired role is acquired by the first successful conditional write without
waiting for any former WATCHDOG, execution peer, private WAL or acknowledgement.
A-016 qualifies the originating installation's release after configuration
publication. A later installation must instead obtain the current coherent ACTIVE
configuration and commissioning receipt from the same fixed document/tab/domain,
and verify its current object metadata with its own authorized SDK connection.

The active-adoption controller validates the original setup/domain/capacity and
commissioning fingerprint, derives only current storage binding from the current
receipt, and checks actual first-run storage, selected credentials, environment
and compatible source. It preserves its own installation, nonce, known operation
history, credential image and selected capabilities, local network-table selection,
topology and private device descriptions/interfaces. Current shared properties
replace only the corresponding existing ordered device identities and aliases.
Unknown or different identities require proper local description, not invented
private data. No former private profile is copied by the product.

Its own closed native STAGING intent precedes a local checkpoint reservation,
immutable complete original archive and separate cache-free stage. A real local
owner confirmation and current first-run qualification precede native PREPARED
and one conditional Main revision with the full previous profile. Stored state
remains INCOMPLETE. Recovery promotes only the same exact protected pending frame,
after fresh role/source/storage/profile proof; no shared or root mutation is sent.
Archive and prior-profile sizes retain the existing budgets.

The protected active receipt may contain one closed CURRENT_ACTIVE_ADOPTION
extension: exact ACTIVE marker, native authority binding and original shared
publication provenance. The new local decision is recorded separately with the
new installation's actual confirmation time and private candidate digest. It does
not impersonate the original shared owner confirmation. Fresh admission validates
both meanings against the actual current document on every use. Restart after
promotion needs only current protected Main/checkpoint/first-run ports; the
adoption WAL/archive/stage and obsolete frozen workloads are not execution grants.

Already committed ACTIVE adoption does not change shared routing identities.
Its explicit local reservation release requires no unresolved local setup,
pending package, election, mutation or effect receipt; current covered transition,
no unfinished root/folder plan, source, actual first-run and current role/force
checks remain mandatory. Shared new BUSY, UNREAD or UNKNOWN records/effects are
preserved and remain available for ordinary observation and exact-operation
no-replay handling. They do not introduce an old-host acknowledgement barrier.
The A-016 non-adoption release still requires zero full current C1 blockers.
Role election itself remains independent of both release paths.

Additive activeAdoption and activeAdoptionReceipt named definitions in the existing
candidate schema retain all former top-level/definition meanings and the same
17-file instruction closure. Only the unreleased development hash changes.
Default entrypoints retain DenyActivation. Source alone accepts no C1-C4 check.
Folder/rootless final publication, runtime/GUI/helper composition and current
source platform/common acceptance gates remain required.
