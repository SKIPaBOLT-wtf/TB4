# Distinct FETCHER enrollment and actual profiles

RP025 adds unreleased protected local selection, an authenticated peer verifier
port, owner approval, fixed-catalogue enrollment/profile codecs and guarded owner
publication. Default runtime activation remains denied. Production peer proof,
integrated FETCHER UI (RP054), coordinated release (RP061) and live deployment
remain later gates; no accepting verifier or copied installation token exists.

FETCHER keeps the UUID generated in its own protected Setup frame. Select only an
approved BALLPARK device with FETCHER role and its already provisioned slot. The
trusted peer adapter must prove the authenticated installation's actual device,
current announcement bytes and compatible runtime build. An opaque alias, name,
address, discovery trust label or remotely supplied boolean supplies no grant.
WATCHDOG must separately confirm first enrollment. Reinstall/device change and
another occupied binding require maintenance rather than silently moving slots.

RuntimeSnapshot is supplied by the actual FETCHER entrypoint/scheduler. Saved
WATCHDOG or FETCHER choices are not its effective profile. Native capture reports
OS/architecture and the running CPython's exact version; presence of another
allowlisted interpreter is UNQUALIFIED until a fixed local executor qualifies it.
Disabled capabilities remain explicit, and a frozen app is not an external Python
binary. No discovered program or arbitrary probe command is executed here.
The scheduler's actual RP011 timing/activity/holds determine poll mode and next
check; untrusted/future/stale clocks never appear fresh. EXITED does not become
proof that a process stopped. A profile never supplies execution authorization.

The existing target catalogue gains compact enrollment and FETCHER profile arrays.
They retain installation/enrollment/profile revisions and full allowlisted facts.
No target work status, artifact, discovery, descriptor, result, cancel, ACK or
history is overwritten. Existing RP009 key/envelope/body budgets are unchanged.
Capacity/headroom rejection happens before local pending save or external write;
no truncation, reset or extra runtime file allocation hides a rejection.

Enrollment requires commissioned root/artifacts, current WATCHDOG owner/forced
request, freshly compatible repository guidance and a current verified peer.
One CAS protects registry/settings/commissioning and every unrelated catalogue.
The exact frozen plan and original pin are durable before sending. Restart or a
lost response only inspects the same after-image. A later owner may confirm its
observed result; no all-sink acknowledgement is needed for role takeover. Old or
newer/different results remain UNKNOWN and are never resent automatically.

Repeated identical verified reports are idempotent. Profile revisions advance
exactly once and samples must advance; stale or future evidence is rejected.
Explicit revocation targets only the exact installation/enrollment generation,
preserves the profile and slot history, and leaves UNKNOWN work intact. General
setup/rollback cannot erase/rebind either local registration package.

Bounded summary pages contain opaque device alias, actual profile, disabled
capabilities, freshness and only this WATCHDOG installation's enumerated credential
availability. Installation UUIDs, credential handles/trust/path/material and
endpoint/topology/hints are absent. A fallback uses its own resolver, and another
installation's resolver is rejected. Native tests use fresh synthetic private
files, not the owner's installed state or real network credentials.

Only owner-approved devices with FETCHER role enter these summary pages; cursor
offsets refer to that eligible sequence. WATCHDOG-only devices remain outside the
projection. A non-FETCHER role carrying a FETCHER binding is inconsistent and
still fails closed, and registration never accepts an unapproved role.
